# Maintaining this

Notes for whoever is maintaining `xgboost-bridge`, including a later version of
whoever wrote it. Not a gate on contributors — see [`CONTRIBUTING.md`](../CONTRIBUTING.md)
for that. This is the material that took measurement to learn and would cost the
same measurement to relearn.

Everything here is about one class of mistake: a change that produces a *plausible
wrong number* rather than an error, and passes.

### Look up the code before changing it

`docs/DECISION_INDEX.md` is keyed by file and symbol. `walk_margin` alone carries
seven entries, several of which reverse a belief that looked sound and was measured
false — which is the situation the index exists for. An intuition that a change is
obviously correct is not evidence, and several of those entries are what an
intuition like that ran into.

It is generated by `tools/build_decision_index.py` from two directions, neither
hand-kept: identifiers the entries mention, and `D0nn` references the source
already carries, attributed by enclosing line range. A test fails if it drifts. After
adding a decision:

```bash
uv run python tools/build_decision_index.py
```

The mention direction alone finds about a third of the entries, and misses D004 and
D053 on `walk_margin` — the oldest entries state a rule without naming the function
that implements it. So if a symbol looks under-covered, the fix is usually to cite
the decision in the code rather than to loosen the matcher: a looser matcher buys
coverage with plausible wrong pointers, and a confident wrong pointer is worse than
a blank.

## The fixture corpus is the one thing that can launder a defect

Change a comparison, regenerate the corpus, watch everything pass. Every guard
downstream — both parity harnesses, the JavaScript suite, the 289 bit-exact margin
assertions — reads the fixture's recorded margin as ground truth.

**The enforcement lives next to the code, in `fixtures/generate/corpus.py`**, which
is where it is read at the moment it matters. That docstring is the authoritative
statement; this section is only the account of why it is worded that strongly.

Two facts are true and neither is sufficient. Ground truth comes from
`booster.predict()`, never from this repository's walk. And the generator re-walks
every row and refuses to write a fixture it cannot reproduce bit-exactly. Both held
while the sample-side `np.float32` cast was reverted and the corpus regenerated
**successfully** — every corpus value was already exact in float32, so narrowing it
is a no-op and a broken implementation routes all of them correctly.

The oracle was never the weakness. The rows were. That distinction is the whole
lesson, and it is easy to lose, because "our fixtures come from XGBoost" is an
accurate sentence that sounds like an answer.

The generator now also asks XGBoost about **1322 rows that narrow onto a threshold**
without equalling it, built from each tree's own splits, and the same revert fails
at generation time. [`fixtures/tests/test_fixture_door.py`](../fixtures/tests/test_fixture_door.py)
pins that probe, because the probe's own failure mode is silence: if the row
construction stops producing rows, the generator reports "no probe rows" and passes.

D064 has the full account.

## Verify a protection by removing it

`tools/revert_harness.py` applies each recorded revert, requires a *named* test to
fail, restores the file byte-exactly, and refuses to start against a dirty tree.

```bash
uv run python tools/revert_harness.py               # Python-side, ~1 min
uv run python tools/revert_harness.py --include-js  # also rebuilds dist/
uv run python tools/revert_harness.py --list        # what it covers, and what it doesn't
```

**A revert that turns nothing red is a finding, not a pass** — the harness fails
when the suite succeeds. Protections here do not decay by being deleted. They decay
by becoming redundant, after which the suite passes without them and nothing
announces it.

It found two cases on its first run, different in kind, and the pair is worth
keeping in mind as the two shapes this codebase produces:

- the **threshold-side cast** in `walk_margin` was genuinely unpinned. Every tree the
  `Predictor` builds is already narrowed at parse time, so the cast is a no-op on the
  only path the suite exercised. It is load-bearing for a caller passing an
  un-narrowed tree, which the public signature permits. Now pinned by its own test.
- the **accumulator's float32 discipline** rests on three overlapping narrowings — the
  seed, the per-leaf cast, the outer cast — and any one of the three suffices alone.
  No single-site revert is detectable, *by construction*. That is recorded as a limit
  under `absorbs` in the harness rather than dressed up as a pin. Someone could remove
  exactly one of the three and nothing here would fail.

The second case amended the rule in `CLAUDE.md`, which used to say "test each
independently, or collapse them to one". It now says: pin the minimal detectable
combination and name what remains unpinned.

When adding a protection, add a revert entry. If the entry reports green, rule out a
mis-specified substitution first — a broken revert and a decayed protection are
indistinguishable from outside, and that has already happened once here.

## NEP 50 changes what a test proves

Worth knowing before writing any test that touches the split comparison. A *Python*
float is weakly typed under NEP 50, so `python_float < np.float32(threshold)` is
evaluated in **float32** — an implementation missing the sample-side cast is
accidentally correct for that caller. A `np.float64` is strongly typed and promotes
the comparison to float64, exposing it.

The same input, spelled two ways, hides or reveals the highest-value defect in the
codebase. Every probe row and every narrowing test here spells it `np.float64`
deliberately.

## Running the gate

`npm run build` **first**. The parity harness refuses a `dist/` older than `src/`
rather than measuring a stale bundle, and 23 tests then fail with a staleness
message that reads like a parity failure.

```bash
npm --prefix packages/js run build
uv run pytest
npm --prefix packages/js run typecheck
npm --prefix packages/js test
uv run python parity/run_parity.py
uv run python parity/run_parity_scale.py
```

Both parity numbers are exactly `0.0`. A small nonzero parity is a bit-level defect,
never a tolerance — diagnose it: a missing narrowing site, a transform in the wrong
space, or an operation that is not correctly-rounded.

### CI runs on dispatch

A push will usually produce no run at all, and that is the trigger rather than the
suite. Every green result on record came from an explicit dispatch:

```bash
gh workflow run ci.yml --ref main
```

`RELEASING.md` assumes this; `VERIFICATION.md` records it as a measurement caveat,
since it means no figure here was confirmed by pushing alone.

## Known open

Both are recorded in `VERIFICATION.md` under "Specific gaps, named rather than
glossed", and neither is a defect:

- the **100,000-row scale parity has only run on darwin/arm64** and is not in CI.
  Those are the rows capable of exposing a float32 defect, which makes it the
  highest-value unrun measurement here.
- **one of the accumulator's three narrowings could be removed with nothing
  failing** — structural, as above, not a coverage gap that better tests would close.
