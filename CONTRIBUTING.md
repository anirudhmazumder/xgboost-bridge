# Contributing

Read this before changing anything numerical. It is short, and one section of it
matters more than everything else in the repository.

## The one way to break this library silently

**If you change how a value is compared, narrowed, or accumulated, and then
regenerate the fixture corpus, you can make the entire test suite agree with your
bug.**

That is not a hypothetical. It is the failure mode this project exists to prevent,
turned inward on the project's own tooling, and it was reachable until recently.
Here is exactly how it worked:

1. Every guard downstream — the parity harness, the JavaScript suite, the 289
   bit-exact margin assertions — treats each fixture's `expected_margin` as ground
   truth.
2. Ground truth is honest: `fixtures/generate/corpus.py` takes it from
   `booster.predict()` and **never** from this repository's own walk. The generator
   also re-walks every row with `walk_margin` and refuses to write a fixture whose
   margin it cannot reproduce bit-exactly.
3. And that refusal still could not see the most important defect. The corpus rows
   are ordinary values, already exact in float32, so narrowing them is a no-op —
   an implementation that skips the sample-side cast routes every corpus row
   correctly. Measured: the sample-side `np.float32` cast was reverted, the corpus
   regenerated, and **generation succeeded silently.**

The generator now also asks XGBoost about **1322 rows that narrow onto a split
threshold** without equalling it, built from each tree's own thresholds. Under the
same revert, generation fails on the first fixture. `fixtures/tests/test_fixture_door.py`
pins that probe, because its own failure mode is vacuity: if the row construction
ever stops producing rows, the generator says so and passes.

So the door is closed for the defect class that walks through it most easily. It is
**not** sealed in general, and you should assume it is open for whatever you are
about to change:

> **Regenerating a fixture is not a way to make a test pass. If a fixture stops
> matching, that is a finding about your change. Report it; do not regenerate over
> it.** The generator says this to your face — *"this is a defect to report, not to
> fix by adjusting the expected value"* — and it is the one instruction in this
> repository with no exception.

Concretely, if `uv run pytest` goes red on a fixture assertion, the correct next
step is never `python -m generate.corpus`. Diff the regenerated corpus and prove
that **only** `provenance.exporter_version` moved (see `RELEASING.md` §3). If
anything numerical moved, stop and read `docs/DECISIONS.md`.

## Before you edit: find what governs the code

[`docs/DECISION_INDEX.md`](docs/DECISION_INDEX.md) is keyed by file and symbol.
Look up what you are about to change and read those entries first. `walk_margin`
alone carries seven, several of which reverse a belief that looked sound and was
measured false.

That file is generated by `tools/build_decision_index.py` from two directions —
identifiers the entries mention, and `D0nn` references the source already carries
— and a test fails if it drifts. If you add a decision, regenerate it:

```bash
uv run python tools/build_decision_index.py
```

Three documents, three directions, easy to confuse:

| Document | Direction |
|---|---|
| `docs/DECISION_INDEX.md` | code → the decisions governing it |
| `docs/DECISION_COVERAGE.md` | decision → the test that pins it |
| `docs/DECISIONS.md` | chronological, with the evidence |

## Verify a protection by removing it

The rule in `CLAUDE.md` is that every protection is confirmed by reverting it **in
isolation** and watching specific tests go red. `tools/revert_harness.py` does that
mechanically:

```bash
uv run python tools/revert_harness.py              # Python-side, ~1 min
uv run python tools/revert_harness.py --include-js  # also rebuilds dist/
uv run python tools/revert_harness.py --list        # what it covers, and what it doesn't
```

**A revert that turns nothing red is a finding, not a pass.** The harness fails
when the suite succeeds. Protections here do not decay by being deleted; they decay
by becoming redundant, after which the suite passes without them and nothing
announces it.

It found two such cases on its first run, and they were different in kind — worth
knowing, because it is the shape of mistake this codebase produces:

- the **threshold-side cast** in `walk_margin` was genuinely unpinned. Every tree
  the `Predictor` builds is already narrowed at parse time, so the cast is a no-op
  on the only path the suite exercised. It is load-bearing for a caller passing an
  un-narrowed tree, which the public signature permits. Now pinned by its own test.
- the **accumulator's float32 discipline** rests on three overlapping narrowings —
  the seed, the per-leaf cast, the outer cast — and any one of the three suffices
  alone. No single-site revert is detectable, *by construction*. That is recorded
  as a limit under `absorbs` in the harness rather than presented as a pin. A future
  edit could remove exactly one of the three and nothing in this repository would
  notice.

If you add a protection, add a revert entry. If your entry reports green, rule out
a mis-specified substitution before concluding anything — that has happened, and a
broken revert and a decayed protection look identical from outside.

## CI runs on dispatch, not on push

**A push will usually produce no CI run at all, and that is not CI being broken.**
Every green result this project has recorded came from `workflow_dispatch`.
Push-triggered runs arrive late or never. So after pushing:

```bash
gh workflow run ci.yml --ref main
```

`RELEASING.md` assumes you know this; the README now says it too.

## The gate

Run all of it. `npm run build` **first** — the parity harness refuses a `dist/`
older than `src/`, and 23 tests then fail with a staleness message that reads like
a parity failure.

```bash
npm --prefix packages/js run build
uv run pytest
npm --prefix packages/js run typecheck
npm --prefix packages/js test
uv run python parity/run_parity.py
uv run python parity/run_parity_scale.py
```

Both parity numbers must be **exactly `0.0`**. A small nonzero parity is a
bit-level defect, never a tolerance — diagnose it. Never loosen, skip or `xfail`
a test: if one is in the way it is telling you something.

## Two things not to add

- **A JavaScript runtime dependency.** Zero is a published property, not a
  preference.
- **A tolerance on a parity gate.** Cross-language parity and upstream accuracy are
  different gates, and conflating them is how a tolerance leaks into the one that
  has none.
